# Naze AI Model Training

Fine-tune a local LLM to generate `.naze` code. The trained model runs via Ollama and integrates with `nazec ai generate`.

## Prerequisites

- **Python 3.10+** with development headers (`sudo apt install python3-dev`)
- **NVIDIA GPU** with 16GB+ VRAM (tested on RTX 4070 Ti Super)
- **CUDA 12.x** with compatible drivers
- **Ollama** installed and running (`ollama serve`)
- **Rust toolchain** (for building nazec)

## Quick Start

```bash
# Create and activate a virtual environment
python3 -m venv ai/.venv
source ai/.venv/bin/activate

# Install Python dependencies
pip install -r ai/requirements.txt

# Run the full pipeline
bash ai/run_pipeline.sh
```

This will:
1. Build `nazec` in release mode
2. Export ~94 `.naze` examples as instruction/response JSONL (uses Ollama to generate descriptions)
3. Validate that all exported examples compile
4. Convert to ChatML format with augmentation (~400 training pairs)
5. Fine-tune Qwen 2.5 Coder 7B with QLoRA (~30-60 min)
6. Export to GGUF and register as `naze-coder` in Ollama
7. Run a smoke test

## Usage

After training:

```bash
# Generate code with the fine-tuned model
nazec ai generate --provider ollama --model naze-coder "Create a todo app with add and delete"

# Or use Ollama directly
ollama run naze-coder "Create a dashboard with metrics"
```

## Pipeline Steps

### Step 1: Export Training Data

```bash
nazec ai dataset export --dir examples --provider ollama --output ai/data/raw_export.jsonl
```

Uses an Ollama model (default: `qwen2.5-coder:7b`, override with `OLLAMA_MODEL`) to generate natural language descriptions for each `.naze` example file. Output is one JSON object per line with `instruction` and `response` fields.

### Step 2: Prepare Dataset

```bash
cd ai && python3 prepare_dataset.py
```

- Loads `docs/AGENTS_SLIM.md` as the system prompt (condensed 9KB language reference, ~2000 tokens — fits within the 4096 training sequence length)
- Converts each pair to ChatML messages format
- Adds 10 curated few-shot examples with hand-written descriptions
- Generates augmented pairs:
  - **Paraphrase variants** (2 per example): Template-based instruction rewording using 5 verb templates (Create/Build/Make/Write/Generate) — triples generation pairs without new code
  - **Error-fix pairs** (~50%): Introduces deliberate errors (missing braces, misspelled keywords, missing quotes), trains model to fix them
  - **Explanation pairs** (~40%): Reverses direction (code in, description out)
- Shuffles and splits 90/10 into `train.jsonl` and `eval.jsonl`

**Expected dataset size:** ~94 raw examples + 10 curated + ~200 paraphrase variants + ~50 error-fix + ~40 explanation = **~400 training samples**.

### Step 3: Fine-Tune

```bash
cd ai && python3 train.py
```

- Base model: `Qwen2.5-Coder-7B-Instruct` (4-bit quantized via unsloth)
- Method: QLoRA (rank 16, alpha 32, dropout 0.05)
- Training: 20 epochs, effective batch size 4, learning rate 5e-5, cosine schedule with 10% warmup
- Sequence length: 4096 tokens
- VRAM usage: ~10-12 GB
- Time: ~30-60 minutes on RTX 4070 Ti Super
- Gradient checkpointing: unsloth optimized (~30% less VRAM)
- Outputs LoRA adapters + Q4_K_M GGUF

### Step 4: Register with Ollama

```bash
cd ai && ollama create naze-coder -f Modelfile
```

Creates the `naze-coder` model in Ollama using the GGUF file and the ChatML template. The `Modelfile` is auto-generated by `train.py` with the correct GGUF path.

## Integration with nazec

The `nazec ai` commands use the trained model at runtime:

- **`nazec ai generate`** — Generates `.naze` code from a natural language description. For fine-tuned models (name containing "naze"), uses a minimal system prompt (~30 tokens). For general models, uses the full `AGENTS_SLIM.md` reference. Retries up to 4 times with validation, using the full reference for retry attempts.
- **`nazec ai fix`** — Fixes broken `.naze` code. Always uses the full language reference regardless of model.
- **`nazec ai dataset export`** — Exports examples as instruction/response JSONL for training.
- **`nazec ai dataset validate`** — Validates that all responses in a JSONL file compile.

The Ollama provider adapter (`crates/nazec/src/prompt_handlers.rs`) streams responses with progress dots and enforces `num_ctx: 16384` and `num_predict` limits.

## System Prompt Strategy

Two system prompts are used depending on context:

| Context | Prompt | Size |
|---------|--------|------|
| Training data | `docs/AGENTS_SLIM.md` | ~9KB, ~2000 tokens |
| Fine-tuned model inference | Minimal one-liner | ~30 tokens |
| General model inference | `docs/AGENTS_SLIM.md` | ~9KB, ~2000 tokens |
| Error correction (retries) | `docs/AGENTS_SLIM.md` | ~9KB, ~2000 tokens |

`AGENTS_SLIM.md` is a condensed version of the full `AGENTS.md` language reference (9KB vs 21.5KB), containing all syntax rules, element/prop lists, 4 complete examples, and anti-patterns. It fits within the 4096-token training sequence length when combined with typical instruction/response pairs (~500-1500 tokens).

## Troubleshooting

**"Python.h: No such file or directory"**: Triton needs Python development headers. Install them with `sudo apt install python3-dev` (or `python3.12-dev` for your specific version).

**"CUDA out of memory"**: Most likely Ollama is still holding VRAM from the export step. The pipeline automatically stops all running Ollama models before training. If it still OOMs, verify with `nvidia-smi` and manually run `ollama stop <model>`.

**Export step times out**: The dataset export calls Ollama for each example. Make sure Ollama is running (`ollama serve`) and has a model pulled (e.g., `ollama pull qwen2.5-coder:7b`).

**GGUF export fails**: Ensure you have enough disk space (~5 GB for the GGUF file). The export also requires `llama.cpp` bundled with unsloth.

**Ollama create fails**: The `Modelfile` is generated by `train.py` with the correct GGUF path. If it fails, check that the FROM path in `ai/Modelfile` points to an existing `.gguf` file. Run `ls ai/data/naze-coder*/*.gguf` to find it. Note: unsloth appends `_gguf` to the output directory name.

**Model generates garbage (repeated dashes/letters)**: This indicates catastrophic forgetting during training. Check that:
- `learning_rate` is 5e-5 or lower (not 2e-4)
- `num_train_epochs` is 15-20 (not 5)
- `MAX_SEQ_LENGTH` is 4096 (training data must fit within this)
- System prompt in training data is `AGENTS_SLIM.md` (~2000 tokens), not the full `AGENTS.md` (~5400 tokens)

**Model generates HTML/CSS instead of Naze**: The system prompt should prevent this. If it still happens, verify the `Modelfile` SYSTEM prompt is set correctly, and check that `num_ctx` is 16384.

**Smoke test hangs (>2 minutes)**: Check that `num_predict` is being passed to Ollama (limits output length). The `prompt_handlers.rs` Ollama adapter should include `"num_predict": req.max_tokens` in options.

**Monitor GPU during training**: Use `nvidia-smi -l 1` or `watch -n 1 nvidia-smi` to monitor VRAM usage and GPU utilization in real time.

|-----------|-------|

| Quantization (training) | 4-bit NF4 via bitsandbytes |
| LoRA rank | 16 |
| LoRA alpha | 32 |
| LoRA dropout | 0.05 |
| Target modules | q/k/v/o_proj, gate/up/down_proj |
| Sequence length | 4096 tokens |
| Training epochs | 20 |
| Learning rate | 5e-5 (cosine schedule) |
| Effective batch size | 4 (batch 1 x accumulation 4) |
| Optimizer | AdamW 8-bit |
| Export format | GGUF Q4_K_M (~4.5 GB) |
| Inference context | 16384 tokens |
| Inference VRAM | ~5 GB |

### Why Qwen 2.5 Coder 7B?

`.naze` is a new language that doesn't exist in any training corpus, so it's reasonable to ask why we start from a code model rather than training from scratch.

**QLoRA preserves base knowledge.** With rank 16 and 4-bit quantization, we train only ~0.5% of the model's parameters. The vast majority of pre-trained weights are frozen — we're steering the model, not replacing it.

**Transfer learning from shared concepts.** Despite novel syntax, `.naze` reuses concepts found across many languages: declarative UI trees (JSX/SwiftUI), reactive state (`state count = 0`), conditionals, loops, string interpolation, and event handlers. A code-trained model already understands these patterns and only needs to learn Naze's specific surface syntax.

**Small dataset demands strong priors.** With ~94 base examples (expanded to ~400 via augmentation), there isn't enough data to teach a model programming from scratch. The code model's pre-existing understanding of structure, indentation, and programming semantics fills the gap.

**Alternative:** If training time or VRAM is a constraint, `Qwen2.5-Coder-3B-Instruct` can be substituted. It trains faster and uses less memory, at the cost of somewhat lower generation quality. Edit `BASE_MODEL` in `train.py` to switch.

## GBNF Constrained Decoding (Experimental)

Naze's PEG grammar can be exported as GBNF for use with llama.cpp's grammar-constrained decoding. This forces the model to only output tokens that form valid `.naze` syntax — pushing first-attempt pass rates toward 100%.

```bash
# Export the grammar
nazec grammar --format gbnf > naze.gbnf

# Clone llama.cpp (not included in repo — gitignored)
git clone https://github.com/ggerganov/llama.cpp ai/llama.cpp
cd ai/llama.cpp && make -j

# Use with a GGUF model
./ai/llama.cpp/llama-cli -m <model.gguf> --grammar-file naze.gbnf -p "Create a counter app"
```

This is separate from the fine-tuning pipeline (which uses unsloth/Ollama). See `docs/PHASE6.md` for the benchmarking roadmap.
